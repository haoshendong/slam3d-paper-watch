方法本质拆解 · What actually changed

是不是微调？

完全不训练：所有检查点都是外部给定的（StarVLA 的 LIBERO 与 RoboTwin 权重），系统只做加载、调度与结果汇总。因此它的“效果”是评测吞吐与结果一致性，不涉及任何权重更新。

有没有额外约束？

约束是接口契约：Policy 必须声明所需观测特征、动作表示、动作块长度与观测步长，评测前会校验特征、dtype、维度和动作形状；基准适配器必须保留原有的任务、初始状态、终止条件与计分；分片与合并要求各实例共享同一构建标识与协议，否则拒绝合并。

推理/后端到底做了什么？

推理侧把模型放进独立进程池，按 GPU 分配副本，请求带 episode id 以便有状态策略按 episode 管理历史与缓存；worker 与副本通过本地请求-应答通信，动作块由 worker 按控制频率逐步执行。调度侧用短探测测吞吐、CPU 占用、GPU 利用率、节流与显存，再按拐点与增益阈值选 (K, g)。

方法本质是什么？

本质是把评测的计算拆成两种资源并分别排队：CPU 侧的仿真与 GPU 侧的推理各自成为可伸缩的池，中间用 episode 级消息解耦；再在这个结构上删掉“没有消费者”的计算（多余渲染、重复初始化、重复校验）。它改变的是评测的执行结构而不是评测定义，没有做的是改变基准规则、改变模型或对不同基准做指标归一。

输入模型检查点与基准套件 → 用 Policy 类与适配器各集成一次，把仿真 worker 与策略副本做成双池并自动搜并发 → 按策略声明的观测步长裁掉无用渲染 → 输出与官方评测逐 episode 等价、快 4–25 倍的结果。

01

桥接价值Bridge

桥接价值

它把“评测”从一次性脚本变成有接口、有调度、有完整性校验的系统，这直接决定我们能否用有限 GPU 时间跑完足够的种子与配置。更值得迁移的是它的分析顺序：先测量一个 episode 的墙钟时间如何分配到仿真初始化、物理步进、渲染、观测传输、策略推理与清理，再判断该加 CPU 还是加 GPU。我们对 SLAM/融合系统做性能剖析时常常只报总耗时或 FPS，缺少这种分阶段、分资源的拆解，结果容易把“等 IO”误判成“算法慢”。

02

方法与模块Method

方法摘要

四个部件：Policy 类（加载检查点、保留模型自己的预处理，声明所需观测特征、动作块长度与观测步长）、基准适配器（包住原生评测器，保留任务与计分）、Control Runtime（把套件展开成 manifest 与工作项，起 K 个模拟器 worker 与 g 个策略副本，收齐逐 episode 记录）与 Simulation Runtime（在工作进程内跑原生评测器，按策略声明的步长跳过不必要的渲染，并复用引擎、缓存种子校验与场景元数据）。并发数由“对角搜索”自动确定：先只加 worker 到吞吐拐点，再按 worker/副本比例加副本，直到增益低于 3% 或触到 CPU/显存上限；跨实例时按工作项下标取模分片，合并时校验覆盖完整性与构建一致性。

可迁移模块

第一，双池独立伸缩：仿真吃 CPU、推理吃 GPU，二者分开后可以单独加，避免“加机器但 GPU 仍闲着”。第二，按消费者声明裁剪计算：策略声明“每 16 步才读一次观测”，评测器就每 16 步渲染一次，其余步复用上一帧；这与我们做多传感器降频、事件触发、按需重定位是同一原则——只算下游真正消费的量。第三，冻结 manifest + 逐 episode 记录 + 幂等发布 + 覆盖校验：任何加速版本都必须能逐条对齐原始结果，这比只报平均成功率可靠得多。第四，短探测代替网格搜索：18 个固定配置要 5.4 小时，7 次探测 8.4 分钟就选到与最优相差 1.2% 的配置，这套“少量探测 + 拐点判据”可以直接用于我们调前端线程数、后端窗口长度等参数。

03

证据Evidence

关键证据与数字

剖析（单卡 RTX 4090，50 个 LIBERO-Long episode）：评测器 55% 时间在 CPU 侧的仿真与逐步处理（其中机器人控制与 MuJoCo 正运动学占大头、物理积分 11%），渲染只占 3%，等动作 26%，建场景与重置 16%；单次推理 55 ms 中 GPU 真正执行 kernel 26 ms，GPU 平均利用率 14.3%。加速：LIBERO-Long 500 episode 中位 671 s（官方 StarVLA 2,990 s，4.45×；RLinf 1,882 s，2.78×；vla-eval 1,016 s，1.52×），吞吐 204.6 steps/s；开 CUDA MPS 后 485 s（6.16×）、282.5 steps/s。等价性：官方 90.2% vs 89.9%（差 −0.3 点，95% 区间 −0.8–0.0），97.9% episode 结果一致；固定 K1/g1 时 500/500 完全一致。RoboTwin Easy：四卡 + 16 步观测 + 两 episode 工作项，500 episode 862 s 对单卡 21,582 s（25.04×，GPU 小时少 6.26 倍），500 个成功结果与终止步全部与三次单卡基线一致；单卡阶梯里观测渲染从 2,100 次降到 132 次，吞吐 2.51×，累计 3.65×。

04

边界与下一步Limits & Next Step

边界与风险

加速成立的前提是策略如实声明观测步长：如果模型实际上每步都读新观测，跳过渲染就会改变输入。RoboTwin 的加速还包含跳过官方评测器的专家 rollout 种子校验与关节位置动作下的 cuRobo 初始化，作者说明在已验证种子缓存下等价，但这意味着结果依赖缓存可信度，换环境或换种子集时要重新验证。多 worker 会带来结果差异：2–20 个 worker 相对单 worker 有 1–28/500 个 episode 结果不同，虽然成功数变化不超过 10；四卡 stride-1 比单卡多 4 个成功（235 对 231，+0.8 点，区间 −2.0–+3.8）。覆盖面也有限：六个适配器只对 LIBERO-Long 与 RoboTwin 给出定量等价性，其余四个基准只有接口层面的说明。

下一步实验

第一条，把它的“冻结 manifest + 逐 episode 对齐 + 等价区间”协议用到我们自己的实验矩阵：固定 episode/序列清单与随机种子，任何并发或降采样改动都必须逐条对齐基线，并报告“结果翻转率”而不只是均值差。第二条，做一次我们系统的分阶段剖析：把前端跟踪、后端优化、回环、地图维护、IO 等待分开计时，同时记录 CPU 占用与 GPU 利用率，找出真正的瓶颈再决定是加线程还是改算法。第三条，借鉴观测步长声明，做一个“按需触发”的 A/B：图像每 N 帧一次、IMU 全速，比较 ATE 与计算量，验证降频是否只删掉了下游不消费的信息。

原文摘要 · Abstract

仿真基准各自带一套评测器、观测布局与动作约定，导致“N 个模型 × M 个基准”要重复集成 N×M 次；同时评测本身很慢：单 GPU 跑 500 个 RoboTwin Easy episode 需要 359.7 分钟，剖析显示仿真占满 CPU 而 GPU 平均利用率只有 14.3%。RoboScope Kit 把每个模型包成一个 Policy 类、每个基准包成一个适配器，保留基准原有的任务、初始状态、终止与计分规则；调度层把模拟器 worker 与 Policy 副本做成两个可独立伸缩的池，用短探测自动搜索并发数，并支持跨实例确定性分片。运行时优化只删掉“策略根本不会读”的计算，例如按动作块边界渲染。单卡 LIBERO-Long 上比官方 StarVLA 评测快 4.45 倍（开 MPS 6.16 倍），成功率等价。

Simulation benchmarks are the standard way to compare robot policies, but each benchmark brings its own evaluator, observation layout, and action convention, and evaluation is slow: 500 RoboTwin Easy episodes with one simulator and one model on one GPU take 359.7 minutes. Profiling the official StarVLA evaluator shows that simulation occupies CPU cores while the GPU averages 14.3% utilization. RoboScope Kit wraps each model once in a Python class called a Policy, and each benchmark once in an adapter around the benchmark's own evaluator, so the benchmark's rules and scoring stay unchanged. Scheduling runs simulator workers and Policy replicas as separate pools, sizes both from measured probes, and shards work deterministically across GPU instances; runtime optimization renders only the observations an action-chunk Policy reads. Adapters cover six benchmark families. On LIBERO-Long with a StarVLA checkpoint on one 48 GiB RTX 4090, the concurrency search selects twelve simulator workers sharing three Policy replicas, which evaluate 500 episodes 4.45$\times$ faster than the official StarVLA evaluation with equivalent success rates, 2.78$\times$ faster than RLinf, and 1.52$\times$ faster than vla-eval at its tuned configuration. With CUDA MPS, which lets the replicas run their kernels concurrently, the search selects sixteen workers sharing four replicas, 6.16$\times$ faster than StarVLA, 3.85$\times$ faster than RLinf, and 2.10$\times$ faster than vla-eval. On RoboTwin Easy, four GPUs with chunk-boundary observation complete the 500 episodes in 14.4 minutes, 25.04$\times$ faster than the single-GPU baseline, with identical success outcomes and terminal steps.
